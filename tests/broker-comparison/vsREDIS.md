# Kafka vs Redis (Pub/Sub · Streams)

> 아래 "축별 비교 ~ 부적합한 이유"는 **Redis Pub/Sub** 기준이다. Redis 에는 지속 로그인 **Streams** 도 있어 결이 전혀 다르므로, 문서 뒤쪽에 [Redis Streams 절](#그럼-redis-streams-는-pubsub-과-급이-다르다)을 따로 둔다.
> (이 저장소의 Redis 는 Redisson 분산락·캐시 용도이며 Pub/Sub·Streams 를 메시징으로 쓰지 않는다.)

## 본질 차이

- **Redis Pub/Sub** = 휘발성 실시간 방송. 발행하면 **그 순간 연결돼 있는 구독자에게만** 전달하고 **저장하지 않는다**. 구독자가 없으면 그대로 사라진다(at-most-once, fire-and-forget). offset·컨슈머 그룹·재생 개념이 없다.
- **Kafka** = 디스크에 쌓이는 재생 가능한 로그. 소비 시점·소비자 수와 무관하게 보존되고, 언제든 다시·여럿이 읽을 수 있다.

한 줄로: Redis Pub/Sub은 "지금 듣는 사람에게만 외치는 확성기", Kafka는 "남겨두고 다시 읽는 로그".

## 축별 비교

| 축 | Kafka | Redis Pub/Sub | 이 워크로드 기준 |
|---|---|---|---|
| 지속성 | 디스크 로그로 보존 | 없음 (휘발) | **Kafka** |
| 전달 보장 | at-least-once (+offset 커밋) | at-most-once (fire-and-forget) | **Kafka** |
| 늦은 구독자 / 리플레이 | 전량 수신 / 재소비 가능 | 유실 / 개념 자체가 없음 | **Kafka** |
| 컨슈머 그룹 · 작업 분배 | 파티션+그룹으로 분배 | 없음 (모든 구독자가 전량 수신) | **Kafka** |
| 순서 보장 | 파티션(키) 단위 보장 | 보장 개념 없음 | **Kafka** |
| 백프레셔 격리 | 느린 소비자는 lag만 늘고 디스크에 보존 | 버퍼 없음 → 못 받으면 드롭 | **Kafka** |
| 라이브 fan-out(동시 연결) | 됨 | 됨 (지연 매우 낮음) | 동급(라이브 한정) |
| 지연(latency) | 낮음 | 매우 낮음 | **Redis** |
| 경량 · 단순성 | 무겁다 | 초경량 | **Redis** |

## 데모로 증명된 것 (`run-comparison.sh`, `run-fanout.sh`)

발행 N건 기준, Redis Pub/Sub 열 vs Kafka 열:

| 시나리오 | Redis Pub/Sub | Kafka |
|---|---|---|
| **늦은 구독자** (발행 뒤 구독) | **0** (전량 유실) | N |
| **리플레이** | **—** (히스토리 없음) | N |
| 동시 연결 소비자 3개 | N / N / N (라이브 fan-out) | N / N / N |
| **나중 합류 소비자** | **0** (발행 뒤 연결은 유실) | N |

→ Redis Pub/Sub 은 **동시에 연결된 구독자들**에겐 잘 뿌린다. 하지만 발행 전/후로 연결이 어긋나면 전량 유실이고, 재소비·작업 분배가 없다. 이건 버그가 아니라 **휘발성 설계**다.

## Redis Pub/Sub 이 적합한 경우 (정직)

- 저장할 필요 없는 **실시간 신호** — 라이브 알림, 프레즌스(접속 상태), 타이핑 표시, 대시보드 틱
- 초저지연 **브로드캐스트** (모든 연결에 즉시)
- 유실돼도 무방한 일회성 이벤트, 초경량 구성

## 이 저장소에서 부적합한 이유

사가·아웃박스·SMS 발송/비용 정합은 **유실이 곧 정합성 붕괴**다:
- 컨슈머 크래시 후 재기동해도 **처리 못한 이벤트가 남아 있어야** 한다 → Pub/Sub은 이미 유실
- 비용 재계산을 위해 **과거를 다시 읽어야** 한다(리플레이) → Pub/Sub 불가
- 당첨자 알림을 **여러 워커로 나눠** 처리 → Pub/Sub은 작업 분배 불가(모두 전량 수신 = 중복 처리)

그래서 Redis 는 이 저장소에서 **분산락·캐시**로만 쓰고, 이벤트 전달은 Kafka 가 담당한다.

## 그럼 Redis Streams 는? (Pub/Sub 과 급이 다르다)

Pub/Sub 과 달리 **Streams 는 지속 로그 + 컨슈머 그룹 + ack + 리플레이**를 갖췄다. 두 데모에 Streams 열을 추가해 실측하면 **위의 약점이 사라진다**:

| 시나리오 | Redis Pub/Sub | **Redis Streams** | Kafka |
|---|---|---|---|
| 늦은 구독자 | 0 (유실) | **N (보존)** | N |
| 리플레이 | — (불가) | **N (XRANGE 재조회)** | N |
| 다중 독립 그룹 fan-out | N (동시 연결만) | **N (컨슈머 그룹)** | N |
| 나중 합류 소비자 | 0 | **N** | N |

→ 보존·리플레이·fan-out 축에서는 **Streams 가 Kafka 급**이다. 그래서 이 네 가지만으로는 Kafka 우위를 주장할 수 없다.

### 그래도 Kafka 가 Streams 보다 나은 축 (스케일·내구성·생태계)

| 축 | Kafka | Redis Streams |
|---|---|---|
| 파티션 수평 확장 | 토픽을 여러 브로커에 분산, 키→파티션 라우팅 내장 | 스트림 하나 = **한 키 = 한 샤드(한 노드)**, 수동 샤딩 필요 |
| 대용량·장기 보존 | 디스크 기반, 수십 TB·수 주 | **메모리 기반** — 워킹셋이 RAM 에 묶임 |
| 내구성 보장 | RF·ISR·`acks=all` → ack 무손실 | 복제 **비동기 기본** → 페일오버 시 ack 유실 가능 |
| 생태계 | Connect·Streams·ksqlDB·트랜잭션(exactly-once) | 없음 |

### 반대로 Streams 가 나은 축

- 인메모리라 **서브밀리초 지연**
- 이미 Redis 를 쓰면 **별도 클러스터 없이** 사용, 운영 부담 작음
- `XAUTOCLAIM` 등 **세밀한 per-entry 재전달** (작업큐에 가까움)
- 중소 규모엔 충분

> 솔직히 이 서비스 규모라면 Redis Streams 로도 가능했다. Kafka 를 정당화하는 건 **장기 보존 리플레이·강한 내구성(과금 정합)·독립 스케일 컨슈머**다. 과장 없이 트레이드오프.
> 참고: 스케일·내구성 우위는 로컬 docker 데모로 재현하기 어렵다(브로커 확장·페일오버 무손실). 데모가 보이는 건 "Streams 는 Pub/Sub 과 달리 보존·리플레이·fan-out 이 된다"까지다.

## 결론

> Redis **Pub/Sub** 은 Kafka 의 경쟁자가 아니라 휘발성 실시간 신호용 **다른 도구**다.
> Redis **Streams** 는 보존·리플레이·fan-out 에서 Kafka 급이지만, **파티션 수평 확장·대용량 장기 보존·강한 내구성·스트림 처리 생태계**에서 Kafka 가 앞선다. 규모·내구성 요구가 낮으면 Streams 도 충분한 선택.
